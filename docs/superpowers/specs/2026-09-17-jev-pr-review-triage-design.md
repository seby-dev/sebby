# Jev-backed PR review triage

## Problem

Every PR review currently runs its full agent set regardless of how trivial
the change is. Two workflows are affected:

1. **`pr-review-toolkit:review-pr`** (an installed plugin, not part of this
   repo) dispatches `code-reviewer` unconditionally plus up to four more
   subagents (`pr-test-analyzer`, `comment-analyzer`, `silent-failure-hunter`,
   `type-design-analyzer`) gated only by coarse file-type heuristics ("if
   test files changed"). Each dispatched agent does a full multi-turn read of
   the diff and surrounding files — the dominant token cost in PR review.
2. A global `~/.claude/CLAUDE.md` rule separately mandates running
   `pr-review-toolkit:silent-failure-hunter`, `pr-review-toolkit:code-reviewer`,
   and `semgrep` in parallel before every PR, independent of `review-pr`.

A one-line docs fix or config bump pays the same token cost as a change to an
auth flow. This spec adds Jev (TypeSafe SDK, `typesafe_sdk`, model
`jev-latest`) as a triage layer that narrows which subagents run on
low-risk diffs, while never reducing coverage below today's baseline on
anything Jev doesn't confidently call low-risk.

## Non-goals

- Jev never replaces a review pass — it only decides how much of the
  existing review machinery runs. No finding is generated by Jev; findings
  still come from `code-reviewer`, `silent-failure-hunter`, and the other
  `review-pr` subagents.
- No hook intercepts subagent dispatch. An earlier design considered a
  `PreToolUse` hook matching the `Task`/`Agent` tool to deny dispatches
  directly. Rejected: such a hook never has diff context (`tool_input` only
  carries `prompt`/`subagent_type`, not a change set), and the dispatch tool's
  name is not stable enough to match reliably (`Task` in some contexts,
  `Agent` in others). Triage is an advisory script the orchestrator consults
  before choosing what to dispatch, not a gate that intercepts dispatch.

## Architecture

Three components, all distributed as part of the `sebby-toolkit` plugin
(this repo) except the CLAUDE.md edit, which is global and separate:

1. **`plugin/hooks/scripts/review_triage.py`** — a plain CLI script, not a
   Claude Code hook. Invoked directly (via Bash) by the new skill below with
   an explicit `--base <ref>`, so the diff being scored is never ambiguous.
   Prints a JSON recommendation to stdout.
2. **`plugin/skills/review/SKILL.md`** (new, invoked as
   `/sebby-toolkit:review`) — orchestrates the whole pre-PR review pass:
   runs triage, dispatches the recommended agents/tools, and reports what
   ran and what triage skipped.
3. **`~/.claude/CLAUDE.md`** — the "Security & Review Workflow" section's
   instruction to directly dispatch the three-tool trio is reworded to
   invoke `/sebby-toolkit:review` instead. This is a one-time global edit;
   it is not part of this repo and is shown as an explicit diff before being
   applied.

## Decision logic

Jev appears in exactly one place: deciding whether `review-pr`'s four
non-floor aspects (tests/types/comments/simplify) can be narrowed on a
low-risk diff. Everything else is deterministic:

1. **Candidate aspects** — the same file-type heuristics `review-pr` already
   uses (test files touched → `tests`; new types added → `types`; doc
   comments touched → `comments`) produce a candidate set, unchanged from
   today's behavior.
2. **`silent-failure-hunter` floor** — a separate deterministic pattern match
   (diff touches `try`/`except`, `.catch(`, or other fallback-branch
   patterns) decides whether it runs. This is not Jev-gated: CLAUDE.md's
   existing wording ("any error handling or fallback code → always run
   silent-failure-hunter") already frames it as conditional on content, not
   truly unconditional — this formalizes that check rather than loosening it.
3. **`code-reviewer` floor** — always dispatched. Never subject to triage.
4. **Jev risk score** — one `Score` judgment (same shape as
   `stop_quality_check.py`'s existing usage) rates the whole diff:
   `trivial` / `low` / `moderate` / `high`.
5. **Narrowing rule** — only when the score comes back `trivial` or `low`
   does triage drop the step-1 candidate aspects down to none. `moderate` or
   `high` (or anything Jev fails to classify) keeps the full candidate set
   exactly as `review-pr` would compute it unaided. This makes the design
   provably no worse than today's baseline on any diff Jev doesn't
   confidently call low-risk.
6. **semgrep** — always runs, unconditionally. It is a static-analysis MCP
   tool call, not a Claude subagent dispatch, so its cost is
   findings-output, not diff-reading tokens; there is nothing to save by
   gating it.

## Fail-open semantics

Jev unavailable, the SDK missing, an exception, or a timeout must all
resolve to the `high` risk value — the same value used when Jev simply isn't
consulted. This makes the fail-open direction structurally hard to invert
(there is no separate "skip" boolean to get backwards; "unscored" and "high"
are the same code path). `TYPESAFE_API_KEY` unset behaves the same way,
consistent with the three existing Jev hooks.

## Rollout controls

- `SEBBY_REVIEW_TRIAGE_MODE` env var: `shadow` (proposed default) logs what
  would have been narrowed and why, to a local file, while still
  recommending the full candidate set — so real PRs can be sampled before
  trusting real narrowing. `active` applies real narrowing. `off` is a hard
  kill switch (behaves identically to Jev being unavailable).
- The skill's final report always states what ran and what triage
  skipped or (in shadow mode) would have skipped, with the reason. A silent
  reduction in coverage is treated as a bug in this design, not an
  acceptable outcome.

## Portability requirements

This repo's plugin scripts run under whatever `python3` a consuming
project resolves on `PATH`, not a bundled venv — the same constraint the
three existing Jev hooks already have, but currently undocumented:

- `plugin/README.md`'s configuration table gets a new row: `typesafe_sdk`
  (the `judgement` extra) must be importable by that `python3`, and
  `TYPESAFE_API_KEY` must be set, or triage is fully inert (always
  recommends the full set — safe, but silent about why no savings appear).
- `pr-review-toolkit` is not guaranteed to be installed in every consuming
  project. `plugin/skills/review/SKILL.md` needs an explicit fallback for
  its `review-pr` dispatch step, mirroring the existing convention in
  `plugin/skills/feature/SKILL.md` ("If X isn't available, do Y manually
  instead of skipping this step") rather than failing when the plugin is
  absent.

## Testing

Mirrors the style of `tests/plugin/test_stop_quality_check_jev.py`:

- Mock `TypeSafeClient`; assert exception, missing API key, missing SDK,
  and timeout all resolve to the full candidate set (`high`).
- Assert the `silent-failure-hunter` trigger fires/doesn't fire correctly
  against fixture diffs, independent of any Jev mocking.
- Assert `shadow` mode never changes the actual recommended set returned to
  the caller, only the logged would-have-been decision.
- Assert `off` behaves identically to Jev-unavailable.

## Out of scope / open questions

- Exact regex/AST patterns for the `silent-failure-hunter` trigger and the
  step-1 candidate-aspect heuristics are implementation details for the plan,
  not fixed by this spec — they should track `review-pr`'s own heuristics
  where they already exist, to avoid divergence.
- Default base ref resolution (e.g. `git merge-base HEAD origin/main`) and
  how a project overrides it are left to the implementation plan.
- Whether to eventually extend triage to other `review-pr` consumers beyond
  this repo's own `feature` skill is not addressed here.
