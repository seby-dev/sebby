# QA swarm

This skill runs a swarm of testers against a feature in an isolated copy of the app and produces one report with reproduction steps and evidence. It changes no code and fixes nothing. It can show that the attacks it tried fail; it can't show the app is unbreakable.

This version dispatches `qa-tester` (a Sonnet 5.5 agent that writes and runs reusable scenarios), `adversarial-tester` (a Sonnet 5.5 agent that tries to break the feature with bad input, double submits, navigation mid-flow, expired sessions, and races between tabs and users), and `security-tester` (an Opus 5.5 agent that tests the app's own security controls on the local instance). It also runs `loadgen.py` beside a batch when the project enables load, starts the instance behind Caddy for a security run, and runs a restart phase that checks what a restart keeps and clears.

## Before you start

- The project supplies `.claude/qa.toml`. Its `schema_version` must be one you know (`1`).
- The user gives the feature: its spec or plan, and a brief. Read `git diff main...HEAD --stat` for the changed routes and components.
- Read `browser.md`, `scenarios.md`, `collisions.md`, `security.md`, and `report-format.md` in this skill's folder.

## The run

1. Read `.claude/qa.toml`. If the file is missing, its `schema_version` is unknown, or a needed section is absent, stop and tell the user. Then run `scripts/qa_env.sh scenario-run --check`. If a key is missing, it stops and names the variable (never its value); stop and tell the user which variable and file. The `[collisions]` section is optional. When it names a `prepare` command, the project writes each collision scenario's target file with it (step 5). The `[load]` and `[security]` sections are optional too. `[load] enabled` doesn't stop the run: it says whether `loadgen.py` may run beside a batch (step 6). `[security]` names the `restart` command (step 8) and the magic-link limits the security tester works within.
2. If the brief says an instance is already running, use that instance and its run folder, and don't start another. Otherwise, choose a scratch folder for the run (`<scratchpad>/`) and run `scripts/qa_env.sh start --scratch <scratchpad>`. If the brief names a web root, such as a planted-defect worktree, add `--web-root <dir>`: Vite serves that checkout's web app, the backend still runs from the repository, and the guard protects both from writes. If it names a backend root (a planted defect in the backend), add `--backend-root <dir>`: the backend runs that checkout's `src/`, and the guard protects it too. For a security run, add `--caddy`: the app is a production build served through the repository's own Caddyfile over `https://127.0.0.1:<port>`, so the security headers and the CSP exist. It needs a Caddy binary (`CADDY_BIN`, or `caddy` on the `PATH`); without one, `start --caddy` exits 2 and starts nothing, so tell the user and stop, or run without `--caddy` and report the header and CSP checks as skipped. A `--caddy` run is for the security tester and the adversarial tester: a `qa-tester` scenario launches its own Chromium without the run's certificate flag, so don't dispatch a `qa-tester` on it. `start` prints one JSON object with, among others, `run_dir`, `run_id`, `site_url`, `allowed_hosts`, `backend_port`, `outbox` (the folder the run's mail lands in), `caddy`, `skipped_checks` (`["security headers", "content security policy"]` without Caddy), `ca_file` and `browser_config` (with Caddy only), and `swept` (the stale runs it removed). Use a relative or absolute scratch path; it resolves against your current folder. If the start fails, it prints no run folder (its error goes to stderr) and stops what it started. Report its stderr and the `env/*.log` files it names, and know that the next `start` sweeps what's left.
3. Run `scripts/qa_env.sh seed --run-dir <run folder>`, which writes `<run folder>/env/identities.json` (two workspaces, `qa-a` and `qa-b`, each with a director, a transcriber, and a singer, plus two seeded runs, one with a share and one without), then `scripts/qa_env.sh session --run-dir <run folder> --email <address>` once for each identity your testers need, serially, before you dispatch. Use the default `--out`, which writes `<run folder>/state/<address>.json`. Testers only load the state files. Plan any real magic-link sign-in and count it against the limits (5 per address and 20 per client each hour, and an over-limit request is silent): each `security-tester` gets a budget of real link requests, and the abuse batch (step 6) is the only place a burst is allowed. Write a state file for the spare identity that the security tester signs out with (`singer-b@choir.test`, say), and give it to no one else: a sign-out ends every tester's session on that identity.
4. Write a charter for each tester at `<run folder>/testers/<name>/charter.md`: the run folder; the absolute path of `scripts/qa_env.sh`; the tester's persona, identity, and state file; the absolute path of the folder that holds the pinned `playwright-cli` (`browser.md`'s `<cli folder>`); the site origin and the allowlist (the site origin, plus the two sound hosts for browser traffic); for a `security-tester` also `ca_file` and `browser_config` when `caddy` is true, or "no Caddy: skip headers and CSP" when it's false, the direct backend port (`http://127.0.0.1:<backend_port>`, allowed for its labeled "direct backend" probes only), the run's outbox (`outbox` in `start`'s output) for its magic-link tests, the path of `<run folder>/env/identities.json` for its share-token tests, its magic-link budget, its spare identity, whether it's the final abuse batch and the address to exhaust, whether it may run the cost-cap probe (only when it runs alone), and the path of the repository whose source it may read; the feature links, diff stat, and your brief; the ordered scenarios; the `[knowledge]` pointers; the known-artifacts list from `[knowledge]`; the `[forbidden]` rules and this skill's safety rules; the scenario budget it gets; and the warnings (an over-limit magic-link request is silent; the guard hook logs every command; a headless session closes after an hour idle).
5. Prepare each collision scenario in the run, if the brief includes any. Create every participant identity's state file first (step 3). For each scenario, run the project's `[collisions] prepare` command (staff2solfa: `scripts/qa_env.sh collide`) as `<prepare> --run-dir <run folder> --scenario <id> --assign <slot>=<tester> ...`, with one `--assign` for each participant slot. It writes `<run folder>/shared/<id>/target.json` and prints it. It refuses an unknown scenario, a bad slot or tester name, a slot with no `--assign`, one tester on two slots, a seeded run with no title, a barrier folder that an earlier batch used, a second scenario that consumes a resource an earlier one in this run already consumes, and a second prepare of a scenario that consumes a resource. For an input error, read its message, fix the input, and run it again. A scenario that consumes a resource is prepared once per run, so check its `--assign` values before you run it; a refused second prepare needs a fresh run. If `qa.toml` names no `prepare`, write `target.json` by hand in the schema in `collisions.md`. Put all of a scenario's participants in the same batch (at most three). Scenarios that share a `needs` resource (two scenarios on the seeded run, for example) run in different batches, never in the same batch. Copy the target path, the tester's slot, and the barrier command into each participant's charter, written with the absolute path of this skill's folder: `bash <skill folder>/barrier.sh wait <barrier.dir> <tester> <barrier.count> <barrier.timeout_seconds>`. The charter tells each participant to run its scenario first, right after it reads the charter and the guides, before any free-form testing, and never to change a resource that another scenario's `target.json` names (such as the seeded share or a seeded run) outside its own scenario; it lists every other scenario's `target.json` path in the run. It tells each participant to run the barrier command exactly as the charter writes it, to get into position (the page open, the snapshot taken, the ref noted) before it runs that command, and to run it with the Bash tool's `timeout` set to 600000; if the tool stops it, the participant records the scenario as abandoned and never re-runs it. Dispatch a scenario's participants at once, in the same batch. A scenario that `consumes` a resource (a share revoke, for example) runs last among the scenarios that need that resource, and only one scenario that consumes a given resource runs in a run: re-seeding is out of scope. Only `adversarial-tester` joins a collision scenario, because the `qa-tester`'s executor can't wait at a barrier.
6. Dispatch up to three agents at once (`qa-tester`, `adversarial-tester`, and `security-tester`), each by its typed agent with no `model` override. If there are more than three, run them in batches of three and start the next batch only when the previous one ends. A collision scenario's participants always share a batch. The run's session cap in `qa.toml` limits live browsers. When `[load] enabled` is true, run `loadgen.py` beside a batch, in the background: `python3 "${SEBBY_ROOT:-$HOME/Developer/sebby}/claude/skills/qa-swarm/loadgen.py" --config .claude/qa.toml --run-dir <run folder> --state <state file> --seed <n>`. It sends the configured mix to the site origin only, clamps to 8 concurrent requests, 20 a second, and 300 seconds, and refuses any target outside the allowlist, or a `--state` file with no cookie for the site, before it sends anything (exit 64). It stops early after five failures in a row: connection failures, or `502`, `503`, or `504` from the proxy, which a dead backend behind Caddy gives (exit 3), and `stop_reason` names them. The summary's `error_types` counts each connection failure by its type, so a TLS verification failure doesn't read as a dead instance. It writes `<run folder>/load/summary.json`. With three testers in a batch, keep load off unless the user asks. Dispatch a `security-tester` whose charter allows the cost-cap probe (rule 3 in the safety rules) only in a batch where it runs alone, and say so in the charter. Run rate-limit abuse in a final batch, alone, after every other tester has finished: one `security-tester` whose charter says it's the final batch, and no `loadgen.py` beside it.
7. When a batch finishes, run `git status --porcelain` in the repository under test and report any change as a violation. Read each tester's `testers/<name>/commands.log` and `testers/_unattributed/commands.log` (the guard logs a command with no `testers/<name>` path there) for off-allowlist hosts and denied commands. For each collision scenario in the batch, run `bash "${SEBBY_ROOT:-$HOME/Developer/sebby}/claude/skills/qa-swarm/barrier.sh" spread <barrier.dir>` and keep its output. Its `outcome` is authoritative, not a participant's exit code. Its `released_count` must equal the number of `acted` entries. A `released_count` greater than the number of `acted` entries means a released participant never recorded acting (a SIGKILL, which can't be trapped, or a failed write); fewer means a participant arrived after the release, which isn't a real collision for that participant. Either way, report that scenario as "not a real collision", not as passed. Then run `ls <run folder>/shared/<id>`: it should hold only `target.json` and the barrier's own files.
8. Restart phase, for a security run, after every tester has finished (the final batch included). If `[security] restart` names a command, run it as `<restart> --run-dir <run folder> --probe-email <the address the abuse tester exhausted>`. It stops only the backend and starts it again on the same port, with the same key and data folders, so the proxy keeps working; it waits for `/v1/health` and prints one JSON object: `restarted`, `backend_url`, `previous`, `kept` (`spend_ledger`, `saved_runs`, and `shares`, each with `before`, `after`, and `same`), and `cleared` (`magic_link_limit` with `limited_before` and `mailed_after`, when you gave a probe address). Exit 0 means the backend came back; exit 1 means it didn't, so report its `error` and go to step 12; exit 2: not a started run folder or a usage error; report stderr (it also prints a JSON line with `restarted: false`) and go to step 12. `previous` is how the old backend ended: `stopped`, or `gone`; `gone` means the backend had died before the restart, which is a finding. A `same` of `false` is a finding: high for the spend ledger, since the cap depends on it. A `same: null` or `mailed_after: null` with an `error` means that check couldn't run; report it as not checked, not as a finding. `limited_before: false` means the address wasn't over its limit, so the check proved nothing (say so). A `limited_before: true` after a heavy batch can come from the per-client limit (20 an hour) rather than the address's own, so say which batch ran last. `mailed_after: false` is a finding: the limit survived the restart, or the address isn't a member. Put the JSON in the report. Testers never run it.
9. Copy each passing scenario draft from `testers/<name>/scenarios/` into `tests/qa_swarm/scenarios/` in the repository, run it once more in place, and commit it. The orchestrator, not the tester, commits scenarios. A tester never writes inside `tests/`. Don't commit a flaky draft.
10. Reproduce every blocker and high finding once, from its stated steps, and fill in its `Reproduced` field (yes, no, or not attempted). Keep a finding that doesn't reproduce, and mark it not reproduced.
11. Merge and de-duplicate the findings into `<run folder>/REPORT.md`: two findings are one entry if their method, route template, and symptom class match, and the entry lists every tester who saw it. Open with a summary table (ID, severity, title, testers, reproduced), then the findings sorted by severity, then a "Collision scenarios" section (and, when a `security-tester` ran, an "Attacks that held" section that copies every line of each security tester's `held.md`, grouped by tester, and a "Restart phase" section that holds step 8's JSON): each scenario's outcome (`passed`, `finding`, `abandoned`, or `not a real collision`) and its `spread` output. Report an `abandoned` scenario as abandoned, never as passed. Name any check skipped (headers and CSP when `instance.json` says `caddy` is false, with its `skipped_checks`), the scenario and step totals against the budget, the `loadgen.py` summary if it ran, any `vision_forbidden` or `jev_forbidden` lines in the `forbidden_hits` list that `qa_env.sh stop` printed (the `vision_forbidden` lines that a `security-tester`'s cost-cap probe caused are expected: report them as its probe's, with their count, and not as a route that tried a billed call), any label in its `orphaned` list (a process group that outlived its leader, which `stop` can't verify or signal), and any label in its `leaked` list (a session whose close failed, or a group still alive after `stop`).
12. Run `scripts/qa_env.sh stop --run-dir <run folder>`, and give the user the path to `REPORT.md`.

Stop the environment on every exit path: after a failed step, an interrupted run, or a decision to abort. `stop` prints one JSON summary (`stopped`, `skipped`, `orphaned`, `leaked`, `forbidden_hits`), it's safe to run twice, and `qa_env.sh start` sweeps stale runs the next time.

## Safety rules for every tester

1. Check every target against the allowlist before a request. The default is the run's site origin. Refuse any other host, and record the refusal. The one exception is the raw backend URL, which only a `security-tester` may use, for a probe its finding labels "direct backend".
2. No external services and no out-of-band callbacks.
3. No billed call from the app: the guarded backend enforces this, and testers use sol-fa text, MusicXML, or seeded runs instead of photo and PDF reads. The executor's own calls (jev, through the named keys) are the one sanctioned billed exception, and `[budget]` caps them. The one sanctioned photo read is a `security-tester`'s cost-cap probe (`POST /v1/extract` with an image). It's safe because the guarded backend sets `STAFF2SOLFA_FORBID_BILLED=1` and holds no provider key, so the vision call stops at the guard and bills nothing, and it leaves a `vision_forbidden` line in the backend log for each read. It runs only in a batch where that tester runs alone, because it changes the seeded workspace's spend cap.
4. No source edits, `git push`, or `git commit`, and no dev data or dev backend.
5. No `dev-key`, no `.env` reads, and no `scripts/extract_hymn.py` or `scripts/eval_*` scripts.
6. Write only to the tester's own folder in the run. Only the orchestrator's prepare step and `barrier.sh` write in the run's `shared/` folder; a tester never writes there. The guard denies the Write tool in `shared/` but doesn't catch a Bash write, so step 7 lists each `shared/<id>` after the batch.

The guard hook enforces parts of these rules and logs every command. Both are best effort, so steps 7 and 11 check after the fact.
